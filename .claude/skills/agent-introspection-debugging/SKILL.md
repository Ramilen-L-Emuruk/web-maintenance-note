# エージェント内省デバッグ

エージェントの実行が繰り返し失敗する、トークンを消費しているが進捗がない、同じツールでループしている、または意図したタスクから逸脱している場合にこのスキルを使用する。

ワークフロースキルであり、隠れたランタイムではない。人間にエスカレーションする前に、エージェントが体系的に自己デバッグする方法を教える。

## 起動タイミング

- ツール呼び出し / ループ制限の最大回数に達した場合
- 前進のない繰り返しリトライ
- コンテキストの増大やプロンプトドリフトによる出力品質の低下
- 期待と現実のファイルシステム / 環境状態の不一致
- 診断と小さな修正アクションでリカバリー可能なツール障害

## スコープ境界

このスキルの適用対象:
- 盲目的にリトライする前に障害状態をキャプチャする
- 一般的なエージェント固有の障害パターンを診断する
- 封じ込められたリカバリーアクションを適用する
- 構造化された人間が読めるデバッグレポートを生成する

以下の目的には使用しない:
- コード変更後の機能検証 → `verification-loop` を使用
- より狭いスキルが既に存在するフレームワーク固有のデバッグ
- 現在のハーネスが自動的に実行できないランタイムの約束

## 4フェーズループ

### フェーズ 1: 障害キャプチャ

リカバリーを試みる前に、障害を正確に記録する。

キャプチャ対象:
- エラー種別、メッセージ、利用可能な場合はスタックトレース
- 直近の意味のあるツール呼び出しシーケンス
- エージェントが実行しようとしていた内容
- 現在のコンテキスト圧力: 繰り返しのプロンプト、肥大化したログ貼り付け、重複した計画、暴走するメモ
- 現在の環境前提: cwd、ブランチ、関連サービスの状態、期待されるファイル

最小キャプチャテンプレート:

```markdown
## 障害キャプチャ
- セッション / タスク:
- 進行中の目標:
- エラー:
- 最後の成功ステップ:
- 最後に失敗したツール / コマンド:
- 検出された繰り返しパターン:
- 検証すべき環境前提:
```

### フェーズ 2: 根本原因の診断

何かを変更する前に、障害を既知のパターンに照合する。

| パターン | 考えられる原因 | 確認方法 |
| --- | --- | --- |
| ツール呼び出しの最大回数到達 / 同じコマンドの繰り返し | ループまたは出口なしのオブザーバーパス | 直近N回のツール呼び出しの繰り返しを検査 |
| コンテキストオーバーフロー / 推論品質低下 | 無制限のメモ、繰り返しの計画、肥大化したログ | 直近のコンテキストで重複と低シグナルの塊を検査 |
| `ECONNREFUSED` / タイムアウト | サービス利用不可またはポート間違い | サービスヘルス、URL、ポート前提を検証 |
| `429` / クォータ枯渇 | リトライストームまたはバックオフの欠落 | 繰り返し呼び出し回数とリトライ間隔を検査 |
| 書き込み後のファイル消失 / stale な diff | レース、cwd 間違い、またはブランチドリフト | パス、cwd、git status、実際のファイル存在を再確認 |
| 「修正」後もテストが失敗し続ける | 仮説の誤り | 正確に失敗しているテストを特定し、バグを再導出 |

診断の質問:
- これはロジック障害、状態障害、環境障害、ポリシー障害のどれか？
- エージェントは本来の目標を見失い、間違ったサブタスクの最適化を始めていないか？
- 障害は決定論的か、一時的か？
- 診断を検証する最小の可逆的アクションは何か？

### フェーズ 3: 封じ込めリカバリー

診断面を変える最小のアクションでリカバリーする。

安全なリカバリーアクション:
- 繰り返しリトライを停止し、仮説を再述する
- 低シグナルのコンテキストをトリミングし、アクティブな目標、ブロッカー、エビデンスのみを保持
- 実際のファイルシステム / ブランチ / プロセス状態を再確認
- タスクを1つの失敗しているコマンド、1つのファイル、または1つのテストに絞り込む
- 推測的な推論から直接的な観察に切り替える
- 障害が高リスクまたは外部的にブロックされている場合は人間にエスカレーション

現在の環境で実際のツールを通じて実行していない限り、「エージェント状態のリセット」や「ハーネス設定の更新」のようなサポートされていない自動修復アクションを主張しない。

封じ込めリカバリーチェックリスト:

```markdown
## リカバリーアクション
- 選択した診断:
- 実行した最小アクション:
- これが安全な理由:
- 修正が機能したことを証明するエビデンス:
```

### フェーズ 4: 内省レポート

リカバリーを次のエージェントまたは人間に理解可能にするレポートで締めくくる。

```markdown
## エージェント自己デバッグレポート
- セッション / タスク:
- 障害:
- 根本原因:
- リカバリーアクション:
- 結果: 成功 | 部分的 | ブロック
- トークン / 時間の消費リスク:
- フォローアップの必要性:
- 後でエンコードすべき予防的変更:
```

## リカバリーヒューリスティクス

以下の介入を優先順位で実施:

1. 本当の目標を一文で再述する
2. 記憶を信頼する代わりに世界の状態を検証する
3. 失敗しているスコープを縮小する
4. 1つの判別チェックを実行する
5. その後にのみリトライする

悪いパターン:
- 少し異なる表現で同じアクションを3回リトライする

良いパターン:
- 障害をキャプチャする
- パターンを分類する
- 1つの直接チェックを実行する
- チェックが支持する場合のみ計画を変更する

## 他スキルとの連携

- リカバリー後にコードが変更された場合は `verification-loop` を使用
- 障害パターンをインスティンクトまたは後続スキルに変換する価値がある場合は `continuous-learning-v2` を使用
- 技術的な障害ではなく意思決定の曖昧さの場合は多角的分析を使用

## 出力基準

このスキルがアクティブな場合、「修正しました」だけで終わらない。

常に以下を提供:
- 障害パターン
- 根本原因の仮説
- リカバリーアクション
- 状況が改善されたか、まだブロックされているかのエビデンス
