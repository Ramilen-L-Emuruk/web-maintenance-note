# Product Lens — 構築前に考える

このレーンはプロダクト診断を担当し、実装可能な仕様書の作成は担当しない。

永続的な PRD-to-SRS やケイパビリティ契約が必要な場合は、`product-capability` に引き継ぐ。

## 使用タイミング

- 機能を開始する前 — 「なぜ」を検証
- 週次プロダクトレビュー — 正しいものを構築しているか？
- 機能の選択に迷っている場合
- ローンチ前 — ユーザージャーニーのサニティチェック
- 曖昧なアイデアをエンジニアリング計画前のプロダクトブリーフに変換する場合

## 仕組み

### モード 1: プロダクト診断

YC オフィスアワーの自動化版。厳しい質問を問う:

```
1. これは誰のため？（「開発者」ではなく、具体的な人物）
2. ペインは何？（定量化: どのくらいの頻度、どの程度深刻、現在どう対処？）
3. なぜ今？（何が変わって可能/必要になった？）
4. 10つ星バージョンは？（お金と時間が無限なら）
5. MVP は？（テーゼを証明する最小のもの）
6. アンチゴールは？（明示的に構築しないもの）
7. 機能していることをどう知る？（指標、フィーリングではなく）
```

出力: 回答、リスク、GO/NO-GO 推奨を含む `PRODUCT-BRIEF.md`。

結果が「はい、構築する」なら、次のレーンは `product-capability`。

### モード 2: ファウンダーレビュー

現在のプロジェクトをファウンダーの視点でレビュー:

```
1. README、CLAUDE.md、pom.xml、最近のコミットを読む
2. 推論: これは何になろうとしているか？
3. スコア: プロダクトマーケットフィットシグナル (0-10)
   - 利用成長の軌跡
   - リテンション指標（リピートコントリビューター、リターンユーザー）
   - 収益シグナル（価格ページ、課金コード、決済統合）
   - 競争上の堀（コピーが難しいものは？）
4. 特定: これを10倍にする一つのこと
5. フラグ: 構築しているが重要でないもの
```

### モード 3: ユーザージャーニー監査

実際のユーザー体験をマッピング:

```
1. 新規ユーザーとしてプロダクトをクローン/インストール
2. すべての摩擦ポイントを記録（混乱するステップ、エラー、ドキュメント不足）
3. 各ステップの時間を計測
4. 競合のオンボーディングと比較
5. スコア: Time-to-Value（ユーザーが最初の成功を得るまでの時間）
6. 推奨: オンボーディングの上位3つの修正
```

### モード 4: 機能優先順位付け

10のアイデアから2つを選ぶ必要がある場合:

```
1. 候補機能をすべてリスト
2. 各項目をスコア: インパクト (1-5) × 確信度 (1-5) ÷ 工数 (1-5)
3. ICE スコアでランク付け
4. 制約を適用: ランウェイ、チームサイズ、依存関係
5. 出力: 根拠付きの優先順位ロードマップ
```

## 出力

すべてのモードはエッセイではなく実行可能なドキュメントを出力する。すべての推奨に具体的な次のステップがある。

## 統合

組み合わせ:
- `/browser-qa` でユーザージャーニー監査の結果を検証
- `/design-system audit` でビジュアル品質の評価
- `/canary-watch` でローンチ後の監視
- `product-capability` でプロダクトブリーフを実装可能なケイパビリティ計画に変換
