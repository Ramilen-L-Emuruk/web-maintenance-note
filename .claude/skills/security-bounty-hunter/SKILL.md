# Security Bounty Hunter — 実用的な脆弱性発見

広範なベストプラクティスレビューではなく、責任ある開示やバウンティ提出のための実用的な脆弱性発見が目的の場合に使用する。

## 使用タイミング

- リポジトリの悪用可能な脆弱性をスキャンする場合
- Huntr、HackerOne、または類似のバウンティ提出を準備する場合
- 「これは実際に報奨金の対象になるか？」が問題であり、「理論的に安全でないか？」ではない場合

## 仕組み

リモートから到達可能な、ユーザー制御の攻撃パスに偏重し、プラットフォームが日常的に情報提供のみまたはスコープ外として却下するパターンは除外する。

## スコープ内パターン

一貫して重要な問題のパターン:

| パターン | CWE | 典型的な影響 |
| --- | --- | --- |
| ユーザー制御 URL による SSRF | CWE-918 | 内部ネットワークアクセス、クラウドメタデータ窃取 |
| ミドルウェアまたは API ガードの認証バイパス | CWE-287 | 不正なアカウントまたはデータアクセス |
| リモートデシリアライゼーションまたはアップロード→RCE パス | CWE-502 | コード実行 |
| 到達可能なエンドポイントでの SQL インジェクション | CWE-89 | データ流出、認証バイパス、データ破壊 |
| リクエストハンドラーでのコマンドインジェクション | CWE-78 | コード実行 |
| ファイル配信パスでのパストラバーサル | CWE-22 | 任意のファイル読み書き |
| 自動トリガー型 XSS | CWE-79 | セッション窃取、管理者アカウント侵害 |

## スキップ対象

プログラムが別途指定しない限り、通常はシグナルが低いかバウンティスコープ外:

- リモートパスのないローカル限定の `pickle.loads`、`torch.load`、またはそれに相当するもの
- CLI 限定ツールでの `eval()` や `exec()`
- 完全にハードコードされたコマンドに対する `shell=True`
- セキュリティヘッダーの欠如のみ
- 悪用影響のない一般的なレート制限の苦情
- 被害者がコードを手動で貼り付ける必要があるセルフ XSS
- 対象プログラムのスコープに含まれない CI/CD インジェクション
- デモ、サンプル、またはテスト専用コード

## ワークフロー

1. まずスコープを確認: プログラムルール、SECURITY.md、開示チャネル、除外事項
2. 実際のエントリポイントを特定: HTTP ハンドラー、アップロード、バックグラウンドジョブ、Webhook、パーサー、統合エンドポイント
3. 静的ツールが役立つ場合は実行するが、トリアージ入力としてのみ扱う
4. 実際のコードパスをエンドツーエンドで読む
5. ユーザー制御が意味のあるシンクに到達することを証明する
6. 可能な限り最小の安全な PoC で悪用可能性と影響を確認する
7. レポートを作成する前に重複を確認する

## トリアージループの例

```bash
semgrep --config=auto --severity=ERROR --severity=WARNING --json
```

その後、手動でフィルタリング:

- テスト、デモ、フィクスチャ、ベンダーコードを除外
- ローカル限定または到達不可能なパスを除外
- 明確なネットワークまたはユーザー制御ルートがある発見のみ保持

## レポート構造

```markdown
## 概要
[脆弱性の内容と重要な理由]

## 脆弱なコード
[ファイルパス、行範囲、小さなスニペット]

## 概念実証（PoC）
[動作する最小のリクエストまたはスクリプト]

## 影響
[攻撃者が達成できること]

## 影響バージョン
[テストしたバージョン、コミット、またはデプロイ先]
```

## 品質ゲート

提出前の確認:

- コードパスが実際のユーザーまたはネットワーク境界から到達可能である
- 入力が真にユーザー制御である
- シンクが意味を持ち、悪用可能である
- PoC が動作する
- 問題がアドバイザリ、CVE、またはオープンチケットでカバーされていない
- ターゲットがバウンティプログラムのスコープ内である
