# /search-first — コーディング前にリサーチする

「既存のソリューションを探してから実装する」ワークフローを体系化する。

## トリガー

以下の場合にこのスキルを使用:
- 既存のソリューションが存在する可能性が高い新機能の開始時
- 依存関係やインテグレーションの追加時
- ユーザーが「X 機能を追加して」と言い、コードを書こうとする前
- 新しいユーティリティ、ヘルパー、抽象化を作成する前

## ワークフロー

```
┌─────────────────────────────────────────────┐
│  1. ニーズ分析                                │
│     必要な機能を定義                           │
│     言語/フレームワークの制約を特定              │
├─────────────────────────────────────────────┤
│  2. 並列検索（リサーチャーエージェント）          │
│     ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│     │ Maven    │ │  MCP /   │ │ GitHub / │   │
│     │ Central  │ │  Skills  │ │  Web     │   │
│     └──────────┘ └──────────┘ └──────────┘   │
├─────────────────────────────────────────────┤
│  3. 評価                                     │
│     候補をスコアリング（機能、保守性、            │
│     コミュニティ、ドキュメント、ライセンス、依存） │
├─────────────────────────────────────────────┤
│  4. 判断                                     │
│     ┌─────────┐  ┌──────────┐  ┌─────────┐   │
│     │  そのまま │  │  拡張/   │  │ カスタム │   │
│     │  採用    │  │  ラップ   │  │  構築    │   │
│     └─────────┘  └──────────┘  └─────────┘   │
├─────────────────────────────────────────────┤
│  5. 実装                                     │
│     依存関係を追加 / MCP を設定 /               │
│     最小限のカスタムコードを作成                 │
└─────────────────────────────────────────────┘
```

## 判断マトリクス

| シグナル | アクション |
|---------|----------|
| 完全一致、十分にメンテナンスされている、MIT/Apache | **採用** — インストールしてそのまま使用 |
| 部分一致、良い基盤 | **拡張** — インストール + 薄いラッパーを作成 |
| 複数の弱い候補 | **合成** — 2〜3 個の小さなパッケージを組み合わせ |
| 適切なものが見つからない | **構築** — カスタム作成（ただしリサーチの知見を活かす） |

## 使い方

### クイックモード（インライン）

ユーティリティの作成や機能追加の前に、以下を確認:

0. このリポジトリに既に存在しないか？ → `rg` で関連モジュール/テストを検索
1. よくある問題か？ → Maven Central / Spring 公式を検索
2. MCP サーバーはあるか？ → `~/.claude/settings.json` を確認して検索
3. スキルはあるか？ → `~/.claude/skills/` を確認
4. GitHub に実装/テンプレートはあるか？ → GitHub コード検索でメンテナンスされている OSS を確認

### フルモード（エージェント）

重要な機能の場合、リサーチャーエージェントを起動:

```
Task(subagent_type="general-purpose", prompt="
  以下の既存ツールをリサーチ: [説明]
  言語/フレームワーク: Java 21 / Spring Boot 3.x
  制約: [任意]

  検索先: Maven Central、MCP サーバー、Claude Code スキル、GitHub
  戻り: 構造化された比較と推奨
")
```

## カテゴリ別検索ショートカット

### 開発ツール
- リンティング → `checkstyle`、`spotbugs`、`pmd`、`error-prone`
- フォーマット → `google-java-format`、`spotless`（Maven プラグイン）
- テスト → `JUnit 5`、`Mockito`、`Testcontainers`、`AssertJ`
- コミット前 → `maven-enforcer-plugin`、`git-commit-id-plugin`

### AI/LLM 統合
- Claude SDK → Context7 で最新ドキュメント確認
- プロンプト管理 → MCP サーバーを確認
- ドキュメント処理 → `Apache PDFBox`、`Apache POI`、`Apache Tika`

### データと API
- HTTP クライアント → `RestClient`（Spring 6.1+）、`WebClient`（リアクティブ）、`Resilience4j`（リトライ/サーキットブレーカー）
- バリデーション → `Bean Validation`（`jakarta.validation`）、`Hibernate Validator`
- データベース → Spring Data JPA、MyBatis、MCP サーバーを先に確認

### コンテンツと変換
- Markdown 処理 → `flexmark-java`、`commonmark-java`
- 画像処理 → `Thumbnailator`、`imgscalr`
- Excel/CSV → `Apache POI`、`OpenCSV`

## 統合ポイント

### planner エージェントとの連携
planner はフェーズ 1（アーキテクチャレビュー）の前にリサーチャーを呼び出すべき:
- リサーチャーが利用可能なツールを特定
- planner がそれを実装計画に組み込む
- 計画での「車輪の再発明」を回避

### architect エージェントとの連携
architect は以下のためにリサーチャーを参照すべき:
- テクノロジースタックの判断
- インテグレーションパターンの発見
- 既存のリファレンスアーキテクチャ

### iterative-retrieval スキルとの連携
段階的な発見のために組み合わせ:
- サイクル 1: 広範な検索（Maven Central、MCP）
- サイクル 2: 上位候補を詳細に評価
- サイクル 3: プロジェクトの制約との互換性をテスト

## 例

### 例 1: 「デッドリンクチェックを追加」
```
ニーズ: Markdown ファイルの壊れたリンクを検出
検索: Maven Central "markdown link checker"
発見: 専用のツールが少ない → textlint-rule-no-dead-link（Node.js）
判断: 構築 — Maven プラグインとして簡易チェッカーを作成、または CI で Node.js ツールを使用
```

### 例 2: 「リトライ付き HTTP クライアントラッパーを追加」
```
ニーズ: リトライとタイムアウト処理付きのレジリエントな HTTP クライアント
検索: Maven Central "resilience4j spring boot"
発見: Resilience4j + Spring Boot Starter（スコア: 9/10）
判断: 採用 — resilience4j-spring-boot3 を依存関係に追加、@Retry + @CircuitBreaker で設定
結果: カスタムコードゼロ、本番で実績のあるライブラリ
```

### 例 3: 「設定ファイルのバリデーションを追加」
```
ニーズ: プロジェクト設定ファイルをスキーマに対して検証
検索: Maven Central "json schema validator"
発見: everit-org/json-schema（スコア: 8/10）
判断: 採用 + 拡張 — ライブラリをインストール、プロジェクト固有のスキーマを作成
結果: 1 依存関係 + 1 スキーマファイル、カスタムバリデーションロジック不要
```

## アンチパターン

- **すぐにコードを書く**: 既存のものがないか確認せずにユーティリティを作成
- **MCP を無視**: MCP サーバーが既に機能を提供していないか確認しない
- **過度なカスタマイズ**: ライブラリを過剰にラップして利点を失う
- **依存関係の肥大化**: 1 つの小さな機能のために巨大なパッケージをインストール
