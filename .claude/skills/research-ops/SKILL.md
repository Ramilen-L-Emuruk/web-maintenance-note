# Research Ops — エビデンスファーストの調査ワークフロー

ユーザーが何かを調査したい、オプションを比較したい、人物・企業をエンリッチしたい、または繰り返しの検索をモニタリングワークフローに変えたい場合に使用する。

これはリポジトリのリサーチスタックに対するオペレーターラッパーである。`deep-research`、`exa-search`、`market-research` の代替ではなく、いつ・どのように組み合わせて使うかを定義する。

## スキルスタック

関連する場合、以下の ECC ネイティブスキルをワークフローに組み込む:

- `exa-search` — 高速な現行 Web 検索
- `deep-research` — 引用付きマルチソース統合
- `market-research` — 推奨やランク付き意思決定が最終成果物の場合
- `lead-intelligence` — 一般的な調査ではなく、人物/企業のターゲティングが目的の場合
- `knowledge-ops` — 調査結果を永続的なコンテキストに保存する場合

## 使用タイミング

- ユーザーが「調査して」「調べて」「比較して」「誰に話すべき？」「最新の情報は？」と言った場合
- 回答が現在の公開情報に依存する場合
- ユーザーが既にエビデンスを提供しており、それを新しい推奨に反映させたい場合
- タスクが十分に繰り返し発生し、単発の検索ではなくモニターにすべき場合

## ガードレール

- 新鮮な検索が安価なのに、古い記憶から現在の質問に答えない
- 以下を明確に区別する:
  - ソース付きの事実
  - ユーザー提供のエビデンス
  - 推論
  - 推奨
- ローカルコードやドキュメントで回答できる場合、重い調査パスを起動しない

## ワークフロー

### 1. ユーザーが既に提供したものから始める

提供された資料を以下に正規化する:

- エビデンスで裏付けられた事実
- 検証が必要な情報
- 未解決の質問

ユーザーが既にモデルの一部を構築している場合、分析をゼロからやり直さない。

### 2. 依頼を分類する

検索前に適切なレーンを選択:

- 簡単な事実の回答
- 比較または意思決定メモ
- リード/エンリッチメントパス
- 定期モニタリング候補

### 3. まず最も軽いエビデンスパスを取る

- `exa-search` で高速な発見
- 統合や複数ソースが重要な場合は `deep-research` にエスカレーション
- 最終成果物が推奨であるべき場合は `market-research` を使用
- 本当の依頼がターゲットランキングやウォームパスの発見である場合は `lead-intelligence` に引き渡す

### 4. エビデンス境界を明示して報告する

重要な主張について、以下のいずれかを明記する:

- ソース付きの事実
- ユーザー提供のコンテキスト
- 推論
- 推奨

鮮度に敏感な回答には具体的な日付を含める。

### 5. タスクを手動のままにすべきか判断する

ユーザーが同じ調査質問を繰り返す可能性が高い場合、明示的にそう伝え、同じ手動検索を永遠に繰り返す代わりにモニタリングまたはワークフローレイヤーを推奨する。

## 出力フォーマット

```text
質問種別
- 事実確認 / 比較 / エンリッチメント / モニタリング

エビデンス
- ソース付きの事実
- ユーザー提供のコンテキスト

推論
- エビデンスから導かれること

推奨
- 回答または次のアクション
- モニターにすべきかどうか
```

## 落とし穴

- ラベルなしに推論をソース付き事実に混ぜない
- ユーザー提供のエビデンスを無視しない
- ローカルリポジトリのコンテキストで答えられる質問に重い調査レーンを使わない
- 日付なしで鮮度に敏感な回答をしない

## 検証

- 重要な主張にエビデンス種別のラベルが付いている
- 鮮度に敏感な出力に日付が含まれている
- 最終推奨が実際に使用された調査モードと一致している
